#### 1. Rate gates count items that contributed nothing (YS-02)
Folds: Code "A `rate:<key>` gate passes `min_items` on items that contributed nothing" (Blocker; `src/yardstick/metrics.py:44-56`, `runner.py:25-39`, `scorers/llm_judge.py:128`, `gate.py:53-60`) and Code "Two tests assert less than their names and decisions claim" (Minor; `tests/test_backcompat.py:31-35`, `tests/invariants/test_ys02_min_items.py`, `tests/test_rates.py:141-150`).
Observed: 10 items with 1 judged and 9 skipped by the budget give `hits=1 total=1 n_items=10`, and a gate with `min_items: 8` passes. The same happens with a `label-rate` scorer when the target errors on 9 of 10 items. The YS-02 invariant tests cover only `pass_rate` and `mean_score`, which is why this passes the suite. A second test compares a hash with itself, although D-24 says "byte-identical (tested)".
Rank versus lens severity: the lens says Blocker and I keep it at rank 1, with a caveat. The coordinator reproduced it at library level only. Through the CLI's `command` target it could not be reproduced, because that adapter carries no `fields` and the gate fails closed. The realistic routes are an `llm-judge` run that hits its budget cap (the live judge has never been run here) and a `results-file` or `http` target with errored items plus a rate rule. None is on the README quick start or the demo path, so a hiring manager would not see it happen. It stays first because the PRD lists YS-02 as an invariant, D-26 says a rate gate counts "only items the scorer applied to", the tests named for YS-02 do not check it, and the lens's fix is small. It is not a security finding.

#### 2. Gate check wording
Folds: UX "Terminal gate lines print a false-looking inequality under FAIL" (Major; `src/yardstick/gate.py` lines 66, 69, 82; `cli.py` about line 354), Design "Gate 'Checks' cell reads as false statements and a double negative" (Major; `src/yardstick/report/markdown.py` lines 277-291), Code "Report check text contradicts its own verdict after rounding" (Minor; `markdown.py:278-291`, `report/format.py:14-37`).
Observed: the terminal prints `FAIL pass_rate floor: 0.583333 >= 0.85; max_drop: drop 0.416667 <= 0.02`, in fractions, while `compare` and the report use percentages. The report prints "floor: 86.4% >= 90.0% (FAIL)" and "max_drop: drop −22.7 pt <= 2.0 pt (ok)" for a rise. Near a rounding boundary it prints `85.0% >= 85.0% (FAIL)`. The verdicts are right in every case.
3 lenses hit this. All 3 recommend building the text from the rule's numbers with one formatter.

#### 5. Baselines

## How this review was run

- **Target.** A whole-repo review of `main` at `94949eb`. Each lens had its own fresh clone and could run
  commands in it. The docs added by the closeout branch (`NEXT.md`, `docs/DEMO.md`, `docs/RELEASE_NOTES.md`,
  `docs/LINKEDIN_DRAFTS.md`) were not part of the target.
- **Independence.** The five lenses ran in parallel and did not see each other's findings. The product owner saw
  all five reports, the coordinator's re-check notes, and the PRD, decisions log and phase plans. It did not
  review the code for new findings.
- **Severity rule.** Blocker, Major, Minor as each lens assigned them. A suspected finding could not be a Blocker.
  The one Blocker is verified at library level only (see item 1).
- **How the interface was seen.** The HTML reports were rendered in headless Chromium by the Design and
  Accessibility lenses. No desktop browser, no real screen reader, no Firefox or Safari. Markdown reports were
  read as source, not as GitHub renders them.
- **Nothing live.** No LLM call, no API key, no request to a model provider, no run of the `http` target against
  a real service, nothing executed on a GitHub runner.
- **Network use to disclose.** The run's rule was "no request to any real external service". Three things went
  outside the sandbox besides GitHub and the package installs for the repo itself:
  1. The Accessibility lens installed `axe-core` 4.14.1 from the npm registry, as its brief allowed.
  2. The Security lens ran one `pip-audit` lookup against the public advisory service for the 21 locked runtime
     packages (package names and versions only), as its brief allowed.
  3. The Security lens also sent one request it was **not** asked to send: `--http-url
     http://169.254.169.254/latest/meta-data/` while testing URL validation. It carried a dummy suite item and
     the made-up token `test-secret-123`, the sandbox answered HTTP 403, and it was not repeated. No real
     credential existed in the sandbox to leak. It is recorded here because it breaks the letter of the rule.
- **Leftover file.** A UX probe (`-o /nonexistent/dir/x.json`) wrote one file outside its working directory in
  the sandbox. The sandbox refused its removal. It is not in the repo and the sandbox is discarded after the run.
- **Lens reports.** Each lens's full output, with its recommended fixes, is committed unedited beside this
  report in `docs/reviews/FIVE-LENS-2026-11-19-lenses/` (`ux.md`, `design.md`, `accessibility.md`,
  `security.md`, `code.md`). The security findings name weaknesses in a public repo; none is rated above Major
  and none involves a real credential or a hosted system (decision D-77).
